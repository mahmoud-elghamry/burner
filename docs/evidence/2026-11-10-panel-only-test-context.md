# سياق اختبار البانل بالبريدجات — 2026-11-10

## ما قاله المستخدم

الاختبار المتاح هو البانل وحده، مع محاكاة المداخل ببريدجات ونزعها، وربما إحضار ثيرموكابل واحد. ذكر ظهور إنذارات سابقة من نوع Fault وTrip رغم وجود البريدجات؛ لا يوجد نص إنذار محدد أو تسجيل أونلاين. لا نفترض أن كل الـ24 بت كانت نشطة، ولا أن البرنامج المحمّل وقتها هو النسخة الحالية. وافق على رقم دخول للإعدادات ثم طرح تأجيله أثناء الاختبار؛ لم تُفعّل صلاحيات أو تُغيّر في هذه المراجعة.

## ما أثبتته مراجعة الكود الحالي

- كل بيرنر يحتاج `TcOkA AND TcOkB`؛ كل قراءة بين ‎−200 و1500 بعُشر الدرجة. حساس واحد يختبر قناة واحدة، ولا يكفي وحده لإثبات سلامة قناتَي بيرنر مع ترك الأخرى مفتوحة.
- `ReadyToStart` يحتاج سلامة المستوى والحرارتين وE-STOP، وعدم Lockout أو Pause24 أو تريب السكرابر.
- بعد رجوع الكهرباء السكرابر ينتظر RESET. إنذارات البيرنر المحفوظة تحتاج زوال السبب وRUN=0 وشروط RESET الحالية؛ رجوع دخل إلى السليم وحده لا يمسح كل ذاكرة عطل.
- RUN=1 دائمًا ليس وضعًا سليمًا: يمنع بدء البيرنر، وبعد 30 ثانية دون طلب يمسك عطل RUN without request. وعدم وصول RUN بعد طلب الحرارة حتى المهلة يسبب NoStart.
- 23 من الإنذارات مصنفة Fault وواحد Warning؛ اسم الـclass لا يثبت أن كل الإنذارات نشطة أو أن كل إنذار يوقف البيرنرين.

## حدود الاستنتاج والاختبار

البريدجات مناسبة لمحاكاة المداخل الرقمية للوحة منفصلة عن البيرنرات والأحمال الميدانية؛ ليست اختبارًا فعليًا للحساسات أو الاحتراق أو حركة الصمامات. يلزم تحديد حالة كل دخل حسب وظيفته، وليس جعل الكل 1. قنوات TC ليست مداخل 24V، ولا توصل عليها تغذية المداخل الرقمية. لا يُشارك حساس واحد بين قناتين كحل افتراضي؛ يلزم مصدر TC مناسب لكل قناة مطلوبة أو اختبار القنوات بالتتابع مع تسجيل حدود الاختبار. لا يُغيّر منطق الحماية لإخفاء إنذار أثناء الاختبار.

عند إعادة إظهار المشكلة، يسجل نص/ID الإنذار وهل هو نشط أو محفوظ أو تاريخي، وقراءات TE الأربع وحالات المداخل وDB المصدر مقابل عرض HMI، وهوية المشروع المحمّل. إذا ثبتت سلامة الإشارات والمنطق مع ظهور إنذارات مخالفة، يُفحص ربط HMI والاتصال ومزامنة نسختَي PLC/HMI. لا يوجد تشخيص مؤكد للعطل القديم الآن.

مرجع الكارت: [Siemens SM 1231 TC specifications](https://docs.tia.siemens.cloud/r/simatic_s7_1200_manual_collection_enus_20/technical-specifications/thermocouple-and-rtd-signal-modules-sms/sm-1231-thermocouple/sm-1231-thermocouple-specifications?contentId=eBbmTSbCzUtkz_4_ioWYGQ). قطع السلك والقيم التشخيصية تتأثر بإعدادات القناة؛ تُقرأ Diagnostics والقيمة الفعلية بدل افتراض أن البريدج يثبت قياس الحرارة.

لم يُنفذ اختبار أونلاين أو تنزيل أو تعديل كود في هذه المراجعة. المحاكاة الجديدة ما زالت مؤجلة بطلب المستخدم.

## استكمال التوجيه وتجهيز ورقة العرض

المستخدم أكد أن العرض أمام المدير مطلوب **على البانل وحده**، ثم طلب خطوات لكل حساس ومدخل وتغييرها ومتابعة المخارج؛ يريد عرضًا بسيطًا دون إضافة وظائف. أُعدت `docs/تجربة البانل فقط.md` بناءً على قراءة الرسم الأصلي صفحات 10–13 نصيًا وبصريًا، ومراجعة الكود ووصف التشغيل الحالي. الورقة تميّز التوصيلات من V1 عن تغيير الدرين إلى NC واستخدام مخارج H5/H6، وتضع شروط عزل الأحمال ومراجعة النسخة المحملة قبل بدء العرض.

إضافة مهمة للتفسير السابق: لا يلزم تركيب أربعة حساسات فعلية للحصول على أربع قراءات صالحة للعرض المنفصل. [Siemens FAQ](https://www.ad.siemens.com.cn/download/materialaggregation_909.html)، جدول SM1231 TC وفقراته 4 و5، يوضح أن شورت طرفَي القناة مع Internal reference يقرأ حرارة الموديول؛ مع المرجع المبرمج يقرأ المرجع المبرمج. لذلك يمكن تجهيز حساس Type K متغير لقناة، وثلاثة شورتات مستقلة للقنوات الأخرى، بعد تحقق الإعداد والقراءات. إعداد Internal reference السابق موثق في `2026-10-27-tia-hardware-created.md`؛ لم يُقرأ إعداد PLC الورشة أونلاين الآن. لا يدخل 24V على قنوات TC ولا يجمع حساس واحد القنوات بالتوازي. الشورت ليس قياس حرارة تانك ولا إثبات دقة/سلامة الحساس الفعلي.

تجهيز الورقة لم يغيّر أي كود أو مشروع TIA، ولم ينفذ توصيلًا أو تنزيلًا أو اختبارًا فعليًا. عرض الإنذارات داخل صفحة Alarms وصلاحيات Engineer والتحقق التشغيلي تظل أعمالًا مفتوحة كما في STATE؛ وجود خطوات اختبار لا يثبت نجاح تنفيذها.

الفحص المحلي: `check_docs.py` نجح، وكل عناوين IO المستخدمة الـ31 موجودة في الورقة (18 DI و4 TC و9 DO). مراجعة مستقلة محدودة من Sol قارنت الأطراف والعناوين وحالات البداية والاستجابة والأزمنة وإعادة التشغيل مع الرسم والكود، ولم تسجل اختلافًا. هذا فحص للإجراء، وليس نتيجة اختبار لوحة.

المستخدم وضح لاحقًا أن تجهيز BR02 بالكامل ليس متاحًا، ويريد تجربة الجزء الموصل دون اشتراط سلامة كل المنظومة. أُعيد فحص شروط ReadyToStart لكل instance وOutputs وCommon: عطل حرارة/مستوى/Lockout الخاص بـBR02 لا يدخل شرط تشغيل BR01؛ المشتركان هما Sys.EStopOK وScrubber_DB.Tripped. Common يقرأ StartEnabled للاتنين لقفل تعديل الإعدادات فقط، وليس لعمل تريب عام من أي عطل. أضيفت فقرة BR01 وحده وشرح كلمات «مفتاح الاختبار» و«متروك»؛ لا يلزم تجهيز قراءات TC الأربع إلا لتجربة البيرنرين معًا. لا توجد قراءة أونلاين أو تعديل منطق جديد.

بطلب المستخدم جعل الجدول تعليمات توصيل مباشرة، استُبدلت خانة الحالة المجردة بمجموعات: أربع بريدجات XI للحساسات الغائبة، RUN وLOCKOUT بلا بريدج أولًا، أزرار الباب والسلكتور بتسليكها الحالي دون تجاوز، ثم X5 للحرارة بشروطه. تجهيز BR02 في جدول مستقل لاحق فقط. بقيت عناوين الـ31 IO المستخدمة مغطاة، ولم تتغير الأطراف أو السياسة أو الكود.

استكمال شرح RUN: أُضيف تعريف H1 كلمبة طلب تتبع Q0.0 وليست إثبات تشغيل، وجدول حالات RUN المبكر والمتأخر والغائب والفقد أثناء RUNNING. مراجعة الشبكات كشفت تفصيلًا مهمًا: شرط حفظ StartEnabled لا يحتوي نفي RunFb، بينما انتقال IDLE إلى STARTING يحتويه؛ لذلك START مع RUN موجود لا يعني أن السماح لم يُحفظ، وقد يظهر الطلب بعد سقوط RUN قبل عطل الـ30 ثانية. تسلسل الرجوع من خطأ التبكير يبدأ بـSTOP لإلغاء السماح، ثم RUN=0، ثم معالجة السبب وRESET عند الحاجة. أُبلغ المستخدم بوصف الكود دون ادعاء اختبار أونلاين أو تعديل سلوك.
